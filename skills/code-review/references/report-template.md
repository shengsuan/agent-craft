# Finding 规范与报告模板

## 1. Finding 必备字段

每条问题必须包含：

- **标题：** 直接描述问题和后果。
- **严重程度：** Critical / High / Medium / Low。
- **置信度：** 高 / 中 / 低。
- **类别：** Bug、Security、Data、Concurrency、Performance、Architecture、Compatibility、Testing、UI、Deployment 等。
- **位置：** 当前版本中的文件路径和行号，优先锚定 diff 修改行。
- **触发条件与证据：** 具体代码路径、条件、数据流或配置，解释问题为什么会发生。
- **影响：** 对用户、数据、安全、可用性或维护成本的实际后果。
- **修复建议：** 与根因对应的具体修改方向，必要时给出短代码片段。
- **测试建议：** 应增加或执行的验证场景。

不要只给“加强校验”“优化性能”等泛泛建议。不要将相同根因拆成多个 Finding。

## 2. 严重程度

| 等级 | 定义 | 典型影响 |
|---|---|---|
| Critical | 可直接导致重大安全事件、数据大规模丢失或核心服务不可用 | 远程利用、跨租户数据泄露、不可恢复的数据破坏 |
| High | 高概率造成严重功能故障、安全漏洞或重要业务中断 | 权限绕过、关键流程失败、重要数据损坏 |
| Medium | 特定条件下造成明显错误、性能退化或局部功能受损 | 边界条件错误、资源泄漏、明显查询退化 |
| Low | 影响有限但有明确收益或潜在风险 | 小范围兼容性、可维护性或低影响错误 |

按实际影响和触发条件判断，不按代码行数或类别机械定级。

## 3. 置信度

- **高：** 代码路径和触发条件明确，证据充分，结论可直接验证。
- **中：** 有具体证据，但影响取决于部分未确认的运行条件。
- **低：** 仍有关键假设未验证。通常不进入正式 Finding；确需提示时标记为“待确认”，不得与已证实问题混排。

## 4. 标准报告

```markdown
# Code Review 报告

## 1. 审查概述
- 审查范围：工作区 / 分支差异 / Commit / 指定文件
- 基准：base、commit 或工作区状态
- 项目识别：语言、框架、架构、运行/部署环境
- 变更规模：文件数、新增/删除行数
- 总体结论：阻止合并 / 修改后合并 / 未发现阻塞项

## 2. 发现的问题

### [High] 问题标题
- **类别：** 安全 / Bug / 数据 / 性能 / 架构 / ...
- **置信度：** 高
- **位置：** `path/to/file:行号`
- **触发条件与证据：** 代码路径及原因
- **影响：** 实际风险
- **修复建议：** 可执行的修改方案
- **测试建议：** 应覆盖的测试场景

## 3. 审查覆盖情况
- 已检查：文件/模块/类别
- 未检查或受限：项目及原因
- 验证命令：命令、结果；未执行项及原因
- 关键假设：可能影响结论的未确认条件

## 4. 总体评价
- 主要风险与优先修复项
- 是否建议合并及前置条件
```

## 5. 总体结论口径

- **阻止合并：** 存在 Critical/High 问题，或有必须先解决的重大验证失败。
- **修改后合并：** 存在需修复的 Medium/Low 问题，或重要前置验证尚未通过。
- **未发现阻塞项：** 在实际审查范围内没有已确认的阻塞性问题；不等于代码绝对没有 Bug。

没有发现问题时，明确写明：“在本次审查范围和已完成检查中未发现可确认的问题。”并列出主要覆盖类别和未执行验证。不要为了填充报告制造问题。

## 6. 报告前质量门禁

- [ ] 问题由本次变更引入或显著放大，而非无关历史问题。
- [ ] 有明确证据和合理触发条件，不是纯推测。
- [ ] 路径、行号、严重程度和置信度准确。
- [ ] 解释了实际影响，并给出可执行的修复建议。
- [ ] 已合并同根因问题，清除重复或泛泛建议。
- [ ] 所有纳入范围文件均已审或明确列出未审原因。
- [ ] 适用的通用/专项类别已覆盖或标记 N/A。
- [ ] 验证命令、结果、失败和限制均如实报告。
- [ ] 没有把“测试通过”表述为“没有风险”，也没有把未验证假设表述为确定事实。
