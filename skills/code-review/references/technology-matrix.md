# 项目识别与技术专项矩阵

## 1. 识别方法

通过仓库配置和实际代码识别技术栈，不根据目录名称或单个依赖推断。优先检查：项目说明、manifest/lockfile、编译器/运行时配置、构建与测试脚本、CI、Docker/Compose、Kubernetes、IaC 和部署清单。

记录：

- 语言及版本、混合语言子项目和运行时/编译器。
- 框架、核心依赖、数据库、ORM、消息队列及外部 SDK。
- 项目类型：前端、后端、全栈、移动端、桌面端、CLI、库/SDK、数据/ML、基础设施。
- 架构形态：单体、模块化单体、微服务、事件驱动、分层/六边形、插件式、Serverless。
- 目标 OS、容器/云环境、CI/CD 及开发/测试/生产配置方式。

多语言仓库按子项目分别识别，并为每个变更文件映射所属子项目。找不到明确证据时标记未知，不要编造技术栈。

## 2. 语言与框架专项

| 技术栈 | 重点检查 |
|---|---|
| TypeScript / JavaScript / Node.js | `strict` 与类型逃逸、Promise 错误、事件循环阻塞、模块格式、依赖/运行时版本、输入校验、原型污染、路径/命令注入 |
| React / Next.js / Vue / Nuxt / Angular | 状态与生命周期、Hooks/响应式规则、SSR/CSR 边界、hydration、路由守卫、缓存、XSS、组件性能和可访问性 |
| Python / Django / Flask / FastAPI | 类型与运行时差异、可变默认参数、异常吞噬、同步/异步混用、ORM 查询、反序列化、命令/模板注入、依赖隔离 |
| Go | error 处理、`context` 传递、goroutine/channel 生命周期、数据竞争、锁、nil interface、资源关闭、接口兼容性 |
| Rust | ownership/borrow、生命周期、`unsafe` 边界、panic、错误传播、`Send`/`Sync`、异步任务取消、锁与资源释放 |
| Java / Kotlin / Spring | 空值与类型边界、线程池、事务代理边界、异常处理、JPA/N+1、依赖注入、序列化、反射和权限控制 |
| C# / .NET | async/await、取消令牌、`IDisposable`、线程安全、DI 生命周期、EF 查询、异常与 nullable、平台目标框架 |
| C / C++ | 越界、生命周期、所有权、UAF、双重释放、数据竞争、未定义行为、整数溢出、ABI 和编译器差异 |
| PHP / Laravel / Symfony | 输入/输出处理、SQL、模板转义、路由中间件、ORM、事务、会话和 Composer 依赖版本 |
| Ruby / Rails | Strong Parameters、Active Record 查询、回调副作用、线程安全、事务、模板转义和 Gem 依赖 |
| Swift / SwiftUI / Objective-C | ARC/循环引用、线程/Actor 隔离、异步任务取消、状态驱动 UI、权限、Keychain 和平台版本 |
| Dart / Flutter | Widget 生命周期、状态管理、异步 mounted 检查、Build 重复执行、平台通道、权限和资源释放 |
| SQL / 数据库脚本 | 方言兼容、锁与事务、索引、全表扫描、NULL 语义、迁移可逆性和数据破坏风险 |
| Shell / PowerShell | 引号与参数边界、退出码、管道错误、路径空格、权限、临时文件清理和跨平台差异 |
| Terraform / Kubernetes / YAML / CI | 权限过宽、Secret 暴露、资源漂移、默认公开、部署顺序、回滚、资源限制和供应链来源 |

未列出的语言或框架，应根据其官方惯用模式、项目配置和实际依赖制定专项检查，不得因此跳过。

## 3. 架构形态专项

| 架构/项目类型 | 重点检查 |
|---|---|
| 分层 / Clean / Hexagonal | 依赖方向、领域层纯度、端口/适配器边界、事务与基础设施耦合 |
| 模块化单体 | 模块边界、跨模块访问、共享表/共享状态、循环依赖和公共接口膨胀 |
| 微服务 | 服务边界、API 兼容、超时/重试、幂等、服务认证、分布式事务、可观测性和故障隔离 |
| 事件驱动 / 消息系统 | 消息 schema 演进、顺序、重复消费、幂等、死信、重放、背压和消费者兼容 |
| Serverless | 冷启动、无状态约束、超时、并发/配额、权限最小化和临时存储假设 |
| 插件式 / 扩展系统 | 插件隔离、权限边界、版本兼容、生命周期、异常隔离和不可信扩展输入 |
| 前后端分离 | API 契约、鉴权一致性、CORS/CSRF、分页、错误模型和前后端版本兼容 |
| CLI / 桌面应用 | 参数与路径校验、配置/密钥存储、OS 兼容、子进程、升级、崩溃恢复和本地数据安全 |
| 移动应用 | 权限最小化、凭据存储、深链、网络安全、离线同步、生命周期和平台差异 |
| 数据工程 / ML | 数据 schema、数据质量、数据/模型版本、训练与推理一致性、资源成本、隐私和可复现性 |
| 公共库 / SDK | API/ABI 兼容、语义化版本、依赖暴露、运行时支持矩阵、错误语义和文档示例 |

## 4. 环境与交付专项

| 环境/交付方式 | 重点检查 |
|---|---|
| Linux / macOS / Windows | 路径分隔符、大小写敏感、权限、信号、进程管理、换行符、文件锁和原生依赖 |
| Docker / Compose | root 用户、镜像来源、层缓存、Secret、健康检查、端口、卷、网络和构建上下文 |
| Kubernetes | RBAC、ServiceAccount、NetworkPolicy、探针、requests/limits、Secret、滚动发布和回滚 |
| CI/CD | Token 权限、未受信任 PR、脚本注入、制品来源、缓存污染、部署审批和环境隔离 |
| Cloud / IaC | IAM 最小权限、公开资源、网络边界、密钥管理、状态文件、销毁/替换风险和跨环境漂移 |
| 开发/测试/生产多环境 | 配置优先级、默认值、Feature Flag、迁移顺序、环境差异和敏感配置泄露 |

## 5. 适配规则

- 只加载与变更文件及其影响链相关的专项检查；但同一项目的关键跨层依赖不能因文件扩展名不同而忽略。
- 如果变更触及多个技术栈或部署边界，组合适用矩阵，不只选一个“主栈”。
- 新增技术、未知框架或内部平台，先从项目约定、调用方式和边界条件推导风险，再记录尚未确认的假设。
- 专项矩阵用于提示风险，不构成穷尽保证；发现新的攻击面或故障模式时，应增加检查。
